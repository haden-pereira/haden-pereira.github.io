# Incident Response & Log Analysis Fundamentals

## Why this matters

Every security event starts as data: logs, alerts, traces. The speed and structure of your response determine whether an incident is contained or becomes a breach. This post gives a hands‑on, repeatable approach to triage, investigate, and close incidents using logs and lightweight tools.

---

## Quick concepts

- Incident Response (IR): the structured process for detecting, containing, eradicating, and recovering from security incidents.  
- Log Analysis: extracting meaningful signals from logs (system, network, application, cloud) to answer who/what/when/where/how.  
- SIEM: centralizes logs and supports queries, detection rules, and alerting. Not required for fundamentals, but helpful.

---

## Core IR workflow (practical)

1. Detection — an alert or unusual log triggers attention.  
2. Triage — decide priority (false positive, benign, or security incident).  
3. Containment — isolate affected hosts/services.  
4. Investigation — collect logs, timelines, indicators of compromise (IOCs).  
5. Eradication & Recovery — remove root cause, patch, restore systems.  
6. Lessons Learned — update playbooks, improve detection.

Actionable triage checklist:
- Who reported/detected the event and how?
- What assets are involved (hostnames, IPs, user accounts)?
- Is the event isolated or widespread?
- Immediate containment step (disable account, isolate host)?
- Preservation: snapshot evidence and collect logs.

---

## Log analysis: start with three questions

1. What changed? (new process, outbound connection, config change)  
2. Who/where did it originate? (user, host, IP)  
3. When did it start/stop? (timeline)

Build a timeline:
- Gather logs from endpoints, firewalls, proxies, and apps for ±24–72 hours around the event.
- Normalize timestamps to UTC.
- Sort events by time and correlate by session IDs, user, or connection.

## Lightweight tools & examples

Shell parsing for quick triage:
- Find suspicious connections in proxy/access logs:
```bash
# common nginx/Apache access log grep for a potential attacker IP
grep "192.0.2.45" /var/log/nginx/access.log | tail -n 50
```

- Count failed auths per user:
```bash
grep "Failed password" /var/log/auth.log | awk '{print $11}' | sort | uniq -c | sort -nr | head
```

- Use jq to inspect JSON logs:
```bash
# filter JSON logs for errors and print timestamp + message
jq -r 'select(.level=="error") | "\(.timestamp) - \(.message)"' app-logs.json
```

SIEM query examples:
- Splunk SPL:
```
index=os sourcetype=linux:syslog "sudo: authentication failure" | stats count by user, host
```
- Elastic/Kibana KQL:
```
event.dataset: "system.auth" and message: "failed"
```

## Investigation: what to collect

- Host evidence: process list, running services, open network sockets, installed packages.
- Logs: system logs, application logs, firewall/proxy, cloud audit logs, authentication logs.
- Network: pcap or flow data if available (start capturing relevant interfaces).
- Credentials/IAM: check for suspicious token creation or permission changes.

Command examples (run from an admin shell during IR):
```bash
# Linux snapshot collection (example)
ps aux > /tmp/ps.out
ss -tunap > /tmp/sockets.out
sudo ausearch -ts recent > /tmp/audit-events.out
```

Always document actions and preserve originals (copy files, don't edit).

## Hypothesis-driven investigation

Create a short hypothesis and test it. Example:
- Hypothesis: "Suspicious outbound to 198.51.100.7 is exfiltration from host web01."
- Tests:
  - Search web01 logs for connections to that IP.
  - Check process that opened connection (ss/netstat + lsof).
  - Check file modification times and large outbound transfers.

If hypothesis is disproven, refine and iterate.

---

## Containment & recovery tips

- Contain first, ask questions later: isolate the host or block the IP in firewall rules if evidence is strong.
- Preserve forensic evidence before rebooting or wiping disks.
- Apply fixes (patch, rotate credentials) and validate with logs that the behavior stopped.
- Communicate: inform stakeholders with concise status and next steps.

## Building a basic IR playbook (skeleton)

- Title: Suspected Data Exfiltration
- Trigger: Large outbound transfer or data‑leak alert
- Initial actions: collect host logs, capture netflow/pcap, isolate host
- Investigation steps: timeline, identify processes, check accounts
- Containment: block egress IPs, revoke tokens
- Recovery: rebuild host from known-good image
- Postmortem: root cause, detection gaps, runbook updates

You can store this as markdown or as simple YAML used by on-call tools.

---

## Detection improvements to prioritize

- Centralize logs (syslog, cloud audit, app logs) with retention policy.
- Create baseline alerts for sudden volume spikes, privilege escalation, and unusual lateral movement.
- Log enrichment: append asset owner, environment (prod/dev), and business criticality.
- Automate basic triage (e.g., automatically collect key logs when alert fires).
